# Лабораторна робота 1. Реєстр задач із перевіркою AI-пропозицій (SDD)

## 1. PM Decision Brief (Обґрунтування рішення та межі AI)

### Контекст і проблема
Після робочих зустрічей учасники команди фіксують домовленості короткими повідомленнями у чатах. При ручному перенесенні у трекер частина задач губиться, а при сліпому автоматичному розборі мовною моделлю (LLM) виникає ризик галюцинацій — модель може вигадати відповідального або строк виконання (дедлайн), яких не було в оригінальному повідомленні, що створює фіктивні зобов'язання для команди.

### Користувач та цінність
- **Користувачі:** учасники продуктової команди, проєктний менеджер (PM) та тімліди.
- **Цінність:** швидке перетворення вільного тексту після зустрічі на структуровану задачу в єдиному реєстрі з гарантією, що жодне поле (особливо відповідальний та строк) не буде додумане системою самовільно.

### Межа автоматизації (AI vs Застосунок)
- **Що робить LLM:** виступає виключно як парсер-пропонувач (`proposer`). Вона отримує сирий текст повідомлення і пропонує чернетку структури у форматі JSON (`title`, `description`, `assignee`, `due_date`). Модель не має доступу до сховища, не керує пріоритетами чи бюджетом і не приймає рішення про збереження.
- **Що робить програма (детермінований код):**
  1. Перевіряє межі вхідного тексту до виклику моделі.
  2. Валідує JSON-схему відповіді моделі.
  3. Перевіряє **підтвердження полів вхідним текстом (grounding)**: запропонований `assignee` (відповідальний) та `due_date` (строк у форматі `YYYY-MM-DD`) мають буквально міститися у вихідному повідомленні, а текст не повинен містити суперечливих дат чи відповідальних.
  4. Якщо даних бракує або є суперечність — повертає статус уточнення (`needs_clarification`) без зміни стану сховища. Якщо модель вигадала дані або зламала структуру — відхиляє запис (`rejected` / помилка валідації) без зміни сховища.
  5. Забезпечує повну незалежність ручного створення (`POST /tasks`) та перегляду списку (`GET /tasks`) від працездатності AI-провайдера.

### Відповідальні за ролями
- **Product / Project Manager (PM):** визначає продуктовий контракт, правила підтвердження полів текстом, критерії приймання (AC) та ухвалює рішення щодо запитів на зміну (Change Requests).
- **Розробник (Coding Agent під контролем людини):** реалізує HTTP-сервіс та детерміновану політику перевірки виключно в межах затвердженої специфікації.
- **QA (Незалежна верифікація):** підтверджує виконання контракту автотестами (`pytest`), мутаційним тестуванням та зовнішніми HTTP-перевірками.

## 2. Набір із 10 синтетичних повідомлень та незалежних очікувань (Частина 1)

| ID | Тип сценарію | Вхідне повідомлення (`text`) | Очікуваний результат системи | Очікувані поля (`assignee`, `due_date`) |

| M01 | Звичайний формат | `Підготувати демо; відповідальний: Ірина; строк: 2026-10-09` | `created` (збережено) | `Ірина`, `2026-10-09` |
| M02 | Перефразування (природна мова) | `Домовилися, що до 2026-10-15 Максим оновить документацію API для клієнтів` | `created` (збережено) | `Максим`, `2026-10-15` |
| M03 | Звичайний формат із описом | `Налаштувати бекапи БД: щоденний дамп о 03:00; відповідальний: Олег; строк: 2026-10-20` | `created` (збережено) | `Олег`, `2026-10-20` |
| M04 | Відсутній строк | `Перевірити логування помилок на тестовому сервері; відповідальний: Ірина` | `needs_clarification` (не збережено) | Відсутній `due_date` |
| M05 | Відсутній відповідальний | `Написати інструкцію для нових менторів до 2026-10-18` | `needs_clarification` (не збережено) | Відсутній `assignee` |
| M06 | Суперечність (дві дати) | `Зібрати фідбек від користувачів; відповідальний: Анна; строк: 2026-10-12 або 2026-10-19` | `needs_clarification` (не збережено) | Конфлікт дат у тексті |
| M07 | Суперечність (два відповідальні) | `Провести код-рев'ю модуля авторизації; відповідальний: Ірина; відповідальний: Максим; строк: 2026-10-11` | `needs_clarification` (не збережено) | Конфлікт відповідальних |

| M10 | Збій провайдера (Provider unavailable) | `Забронювати аудиторію для ретроспективи; відповідальний: Максим; строк: 2026-10-14` | `provider_unavailable` (не збережено) | Помилка 503, ручний шлях працює |
